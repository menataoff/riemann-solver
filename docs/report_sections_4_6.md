# 4. Проект программного комплекса (2.1–2.3)

Состояние проекта на 17.11.2026. Реализована часть 1: точный локальный решатель задачи Римана, интерфейс расчёта потока, фабрика с единственной реализацией exact, чтение ограниченного подмножества YAML, текстовая диагностика, экспорт CSV, графики и пять тестов Торо. Сеточного обновления, применения граничных условий, HLL/HLLC/Роу, 2D, MPI/OpenMP и HDF5 пока нет. Ниже действующая реализация отделена от проекта следующего этапа.

## 4.1. Модули и зависимости (2.1)

- Действуют: state.hpp (PrimitiveState, ConservativeState, Flux); wave_function и vacuum; pressure_solver, star_state, wave_speeds; exact_riemann_solver; sample_solution и face_flux; RiemannFluxSolver, ExactFluxSolver, solver_factory.
- Действуют отдельно от численного ядра: config.cpp читает YAML; output.cpp направляет текст в консоль или файл; export_case/profile_export/xt_export/pu_export записывают CSV; Python-скрипты строят PNG; toro_cases и toro_tests хранят эталоны и проверки.
- main.cpp управляет одной задачей Римана: читает Config, вызывает точный решатель, показывает p*, u*, волны, W(S) и поток. Он пока содержит диагностику, специфичную для точного метода. Из-за этого добавления ветви в фабрику недостаточно для полноценного переключения программы на HLL.
- Планируются: eos и переход W ↔ Q; grid и boundary с фиктивными ячейками; scheme и time_step для консервативного шага и CFL; новые реализации RiemannFluxSolver; halo_exchange, параллельный вывод и контрольные точки. Эти компоненты не входят в текущие исполняемые цели.

Схема зависимостей: сплошная часть действует, строка «ПЛАН» показывает будущий контур.

```text
YAML -> config -> main -> exact_riemann_solver -> pressure/star/waves
                |    |-> solver_factory -> ExactFluxSolver -> face_flux
                |    |-> sample_solution; face_flux -> sample_solution
                |-> export_case / export_toro -> CSV -> Python -> PNG

ПЛАН: grid + boundary -> scheme + CFL -> RiemannFluxSolver -> Q
      halo_exchange -> фиктивные ячейки (MPI)
```

Расчётное ядро не читает YAML и не пишет файлы. Экспорт сеточных полей должен быть отдельным потребителем результата шага, без зависимости численного ядра от формата файла. Для MPI между boundary и расчётом потоков потребуется halo_exchange.

## 4.2. Единый интерфейс потока (2.2)

Действующий интерфейс в include/riemann_flux_solver.hpp:

```cpp
virtual Flux solve_flux(const PrimitiveState& left,
                        const PrimitiveState& right,
                        double gamma) const = 0;
```

ExactFluxSolver реализует этот метод через solve_riemann и calculate_face_flux. make_solver(name) сейчас принимает только exact; config.cpp тоже разрешает только method.solver: exact и method.scheme: none. При вакууме точный поток не возвращается, поскольку вакуумное решение не реализовано.

Для нового решателя нужно добавить отдельные .hpp/.cpp, реализовать solve_flux, зарегистрировать имя в solver_factory и разрешить его в Config. Сеточная схема должна вызывать только RiemannFluxSolver; она не должна требовать StarState или WavePair. Для общего main нужно отделить необязательную диагностику точного решателя от базового потока. Нельзя обещать, что один новый класс уже сделает существующий main универсальным.

## 4.3. Хранение состояния (2.3)

Сейчас PrimitiveState содержит rho, u, p; ConservativeState содержит rho, momentum, energy; Flux содержит mass, momentum, energy. Все поля имеют тип double. Функций общего преобразования W ↔ Q и контейнера сетки пока нет. В exact_riemann_solver результат хранит давление, звёздные состояния, типы и скорости волн; массивы CSV создаются только при экспорте.

В будущей сеточной схеме предполагается хранить Q для консервативного обновления, а W вычислять перед получением потоков. Для N внутренних ячеек и g фиктивных слоёв в 1D потребуется N + 2g ячеек. Вариант SoA — отдельный массив double для каждой компоненты Q и два временных слоя. Это проектное решение, а не свойство текущего кода. Индексацию 2D, обмен буферами и размерные масштабы следует определить после согласования структуры сетки. В действующем Config есть gamma, но нет N, CFL и физических масштабов.

# 5. Ввод, вывод и сборка (2.4–2.6)

## 5.1. Входные данные (2.4)

Для воспроизводимого запуска используйте полный действующий файл examples/toro_1.yaml либо копию config.yaml. Обязательные группы: gas.gamma; method.solver=exact, method.scheme=none; domain.x_min/x_max/discontinuity; initial.left/right с rho,u,p; boundary.left/right с type; output.destination/file/sample_x/sample_time. Для type=fixed нужны также rho,u,p в соответствующем boundary. Поля boundary пока проверяются, но не участвуют в расчёте одного разрыва.

Парсер принимает вложенные скалярные ключи с отступами по два пробела и комментарии. Он не принимает YAML-списки, inline-словари и ссылки. Неизвестные и повторные ключи отклоняются. Проверяются конечность чисел, gamma>1, rho,p>0, x_min<x0<x_max, sample_time>0 и sample_x внутри области. Ошибка выводится в stderr, код 1. Вакуум определяется отдельно; prac15 завершает его диагностикой, а export_case не пишет новые CSV и возвращает код 2.

Поля domain.cells, time.cfl, output.times, output.directory, output.format и схема godunov относятся к проекту сеточной версии: сегодня такой YAML не запустится. Для будущей версии понадобятся N>0, допустимое CFL, отсортированные моменты вывода и собственная проверка совместимости схемы с решателем.

## 5.2. Выходные данные (2.5)

prac15 записывает текст в консоль либо в output.file из YAML. Файл перезаписывается при каждом запуске. export_case принимает YAML и необязательный каталог CSV (по умолчанию output/custom); export_toro пишет данные пяти тестов в output/cases/toro_N. Экспорт создаёт metadata.csv, profile.csv, xt_density.csv и pu_curves.csv. Каталог создаётся автоматически. scripts/plot_case.py и scripts/plot_all.py строят PNG по этим CSV; место рисунков задаётся аргументом --figure-dir. output.file не управляет путями CSV и PNG.

metadata.csv хранит параметры и найденное решение, но не содержит commit, дату, компилятор или сведения о запуске. Форматы HDF5/XDMF, контрольные точки и автоматическое версионирование каталогов пока не реализованы. Для будущих сеточных расчётов можно предусмотреть каталог вида output/<case>/<run-id>/ с копией входного файла, полями и метаданными, а для крупных массивов — HDF5/XDMF после выбора библиотек и схемы параллельного вывода.

## 5.3. Сборка и дерево проекта (2.6)

В корне находятся include/ (API), src/ (реализации), tests/toro_tests.cpp, examples/toro_*.yaml, tools/export_case.cpp и export_toro.cpp, scripts/plot_*.py, main.cpp, config.yaml, CMakeLists.txt и requirements.txt. CMake собирает библиотеки prac15_config, prac15_riemann, prac15_toro, prac15_export и программы prac15, toro_tests, export_toro, export_case. Код C++17 не требует внешних библиотек; Python-графика использует numpy и matplotlib.

Проверенная локальная среда: GCC 13.3.0, CMake 3.28.3. Для GNU/Clang цели получают -Wall -Wextra -Wpedantic. Проверка Clang, MPI и HDF5 не заявляется. Команды из корня проекта:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j4
ctest --test-dir build --output-on-failure
./build/prac15 examples/toro_1.yaml
./build/export_case examples/toro_1.yaml output/my_case
.venv/bin/python scripts/plot_case.py output/my_case \
  --figure-dir output/my_case/figures
```

Для Python сначала выполните python3 -m venv .venv и .venv/bin/pip install -r requirements.txt. На кластере возможен последовательный Slurm-запуск после настройки модулей компилятора и сборки; текущая программа не запускает MPI и не использует несколько потоков.

# 6. Параллельность, тесты и совместная работа (2.7–2.10)

## 6.1. План MPI/OpenMP (2.7)

При декомпозиции области MPI-процесс хранит локальные Q и фиктивные ячейки. Перед потоками на внутренних гранях halo_exchange должен обновить фиктивные данные соседей; boundary задаёт физические края. Локальная оценка шага по CFL сводится MPI_Allreduce(MPI_MIN), затем шаг ограничивается ближайшим моментом вывода. Потоки на разных гранях можно считать в параллельном цикле OpenMP; обновление Q выполняется отдельным циклом после барьера. Для воспроизводимости и проверки баланса нужно отдельно определить владение гранями и порядок глобальных редукций. Ни MPI, ни OpenMP сейчас не подключены.

## 6.2. Проверки (2.8)

toro_tests проверяет пять табличных задач: p*, u*, две плотности за волнами, типы и корректный порядок скоростей волн, конечность и положительность плотности/давления W(0). Эталон сравнивается с допуском 0.5% или 1e-5 абсолютно. Выявленная в предыдущей редакции ошибка сравнения с нулевым эталоном исправлена: при reference=0 теперь требуется |value|<=1e-5; добавлена регрессионная проверка, отклоняющая value=1. Автоматический запуск — ctest --test-dir build --output-on-failure.

Следующие полезные проверки: вакуумный порог, W(S) внутри обоих вееров, поток на неподвижной грани, сохранение постоянного состояния. Для будущей схемы — интегральный баланс массы, импульса и энергии, положительность rho и p, сеточная сходимость; затем сравнение последовательной и MPI/OpenMP-версий на одной сетке. Эти проверки пока не следует считать реализованными.

## 6.3. Организация разработки (2.9–2.10)

Репозиторий: github.com/menataoff/riemann-solver. Предлагаемый процесс: отдельная ветка на задачу, проверка CTest, просмотр изменений другим участником и слияние в main. Стиль проекта: четыре пробела, snake_case для функций, PascalCase для типов, const& для входных аргументов. Публичные объявления находятся в include/, реализации — в src/, использование объясняется в docs/ и README.

Разделение следующего этапа между Жилиным Н. А. (EOS и проверки физики), Мыкиным А. С. (сетка, границы, схема и CFL) и Полонским М. В. (приближённые решатели, параллельность и вывод) остаётся предложением для согласования. По текущим файлам индивидуальный вклад не установлен. Перед работой над сеткой нужно согласовать W/Q/F, индексацию, обработку ошибок, формат интерфейса и критерии тестов.

Источники формул: лекция курса §15; тестовые данные — задание «Практика к §15». Текущее состояние реализации сверено с исходным кодом проекта на 17.11.2026.
